# 设计文档：AI 控制协议（客户端 ↔ 我们的服务器）

> 状态：**协议设计 + 客户端骨架已落地**。服务端尚未实现。
> 客户端（Qt 应用）已完成：请求组装、超时、错误提示、**指令白名单执行**。
> 服务器返回什么就执行什么，是这套设计的核心约束，见第 4 节。

---

## 1. 为什么这样分层

作者定下的方向：**所有 AI 请求都发到我们的服务器**，服务器返回本地控制指令，
客户端执行。不采用「客户端直连各家厂商」的做法。

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 客户端直连厂商 | 实现最快、无中间成本 | 用户必须自己申请 Key；换服务商要改客户端；无法统一限流/审计；Key 散落在用户机器上 | ✗ |
| **客户端 → 我们的服务器 → 厂商** | 换模型不改客户端；可按账号配额；可审计与降级；用户不用自备 Key | 需要运维、有带宽与调用成本 | ✓ **采用** |

这套结构也顺带解决了「用户自己填 Key」和「用我们提供的服务」两种用法的矛盾：
**两种用法在客户端是同一段代码**，区别只在请求里带不带用户的 Key（由服务端判断）。

## 2. 请求格式（客户端 → 服务器）

```http
POST <endpoint>
Content-Type: application/json; charset=utf-8
```

```json
{
  "message": "把物理设成当前学科",
  "context": {
    "currentSubject": "math",
    "theme": "dark",
    "provider": "deepseek",
    "availableSubjects": ["math", "phy", "che"],
    "supportedOps": ["ai.set_provider", "ui.close_chat", "ui.open_chat",
                     "ui.open_settings", "ui.set_subject", "ui.set_theme"]
  }
}
```

- `message`：用户原话，不做任何改写。
- `context`：软件当前状态。**这是「AI 能操作软件」的前提**——服务器不知道
  当前有哪些学科、当前是什么主题，就无从生成正确指令。
- `supportedOps`：客户端自报能力。服务器只能从这张表里挑，客户端不认的一律拒绝。

> 认证方式尚未定（见第 6 节）。当前实现不带任何凭据。

## 3. 响应格式（服务器 → 客户端）

```json
{
  "reply": "好的，已经切到物理了。",
  "commands": [
    { "op": "ui.set_subject", "arg": "phy" }
  ]
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `reply` | 否 | 给人看的文字，显示在对话气泡里。可以和 `commands` 同时存在 |
| `commands` | 否 | 要在客户端执行的指令列表，**按顺序执行** |

至少要有其中一个。两者都空 → 客户端报「服务器返回了空回复」。

---

## 4. 指令白名单（安全边界，不可协商）

客户端只执行下列 `op`。**服务器无法让客户端做白名单之外的事。**
这是整套设计的核心：即使服务器被攻破、或模型被提示注入，破坏也限制在这几个动作内。

| op | arg | 效果 |
| --- | --- | --- |
| `ui.set_subject` | 学科 id（如 `phy`） | 切换当前学科 |
| `ui.open_chat` | 无 | 打开对话面板 |
| `ui.close_chat` | 无 | 关闭对话面板 |
| `ui.open_settings` | 无 | 打开设置 |
| `ui.set_theme` | `dark` / `light` / `star` | 切换主题 |
| `ai.set_provider` | 服务商 id | 切换 AI 服务商 |

实现见 [src/ui/control_command.cpp](../src/ui/control_command.cpp) 的 `AllowedOps()`。

**明确不做的事**（即使 AI 要求也不做）：

- 不执行任意脚本、不读任意文件路径、不发起任意网络请求
- 不修改仓库或系统配置
- 不读写 API Key
- 不删除用户资料

新增指令的流程：先在 `AllowedOps()` 加白名单项 + 执行分支，
再更新本文第 4 节表格，最后服务端才能使用。**不能先让服务端发、客户端再补**。

### 4.1 参数校验

- `op` 为空 → 拒绝并提示
- `op` 不在白名单 → 拒绝，并把 `op` 名显示给用户（便于排查是服务器写错还是客户端太旧）
- 需要 `arg` 的指令缺 `arg` → 拒绝
- 白名单里有但没写执行分支 → 报「指令未实现」，视为客户端 bug

拒绝都会通过 `CommandBus::rejected` 信号反映到界面上，**不会静默吞掉**。

## 5. 客户端的失败处理

| 情况 | 处理 |
| --- | --- |
| 未配置服务器地址 | 直接提示「还没有配置服务器地址」，不发请求 |
| 地址格式非法 | 提示「服务器地址无效」 |
| 上一条还在处理 | 提示「上一条消息还在处理中」，不并发 |
| 超时（60 秒） | 提示「服务器超时（60 秒）」 |
| 网络错误 | 显示底层错误文本 |
| 返回非 JSON | 提示「服务器返回的不是合法 JSON」 |
| 空回复 | 提示「服务器返回了空回复」 |

**所有失败都必须显示在对话里**。宁可让用户知道没通，也不能让人以为 AI 在思考。

## 6. 尚未决定的部分

1. **认证**：登录后怎么带凭据？Bearer token、Cookie，还是每次请求签名？
   与 T-024（账号登录）联动。
2. **「用我们提供的服务」怎么计费/限额**：免费额度、按次、还是绑定自己的 Key 就不限。
3. **用户自备 Key** 走哪条路：也发到我们服务器中转（简单但要把 Key 交给我们），
   还是客户端直连厂商（有 CORS 问题，桌面端可绕过但移动端麻烦）。
   目前实现按「全部经服务器」写，这一条若改会动到 `ai_client.cpp`。
4. **流式输出**：当前是非流式（一次返回完整 JSON）。真要做打字机效果，
   需要改成 SSE 或分块传输，指令部分要等整个 JSON 完整才能执行。
5. **多轮历史**：当前每次只发一条 `message`，没有对话历史。要不要带、
   带多少轮、由服务器存还是客户端存。
6. **能力协商**：`supportedOps` 现在由客户端写入请求，服务器理论上可以忽略。
   是否需要服务器返回它理解到的能力列表，便于排查版本不匹配。
